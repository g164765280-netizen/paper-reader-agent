# Agent 开发学习路线（从 0 到 1）

> 以本项目（领域文献速读 Agent）为完整案例，按顺序做一遍，你就掌握了 LLM Agent 开发的主干。
> 每一步都有对应的代码、产出和"坑"，全部实测过。

---

## 阶段 0：把问题想清楚（最重要，别跳过）

- **明确目标**：你的 agent 帮谁、解决什么？（本项目：帮研究生新生快速读文献）
- **诚实边界**：LLM 能做什么、不能做什么。（本项目：能检索+抽取+描述，不能"可靠推理专家"）
- **产出**：一段话的项目定位。

## 阶段 1：RAG 检索增强生成

- **学什么**：为什么 LLM 会幻觉？为什么检索能减少幻觉？
- **做什么**：论文语料 → 分块 → 向量化（bge-m3）→ FAISS/BM25 混合检索 → 生成（Qwen）
- **产出**：`src/rag/` 的完整 RAG 管线
- **坑**：① 分块粒度影响检索质量；② 中英文要选对 embedding；③ 慢磁盘会让模型加载极慢

## 阶段 2：评测先行（本项目最值钱的方法论）

- **学什么**：为什么要先建评测集？什么是"留出集隔离"？什么是"Oracle 对照"？
- **做什么**：留出论文不进语料；每条题带金证据；`Base+正确证据` vs `Base+RAG` 分离检索错误与生成错误
- **产出**：`src/eval/` 的评测 harness
- **坑**：金证据必须含答案（否则测的是假能力，本项目真实踩过：金证据截断导致数字忠实"假性 8%"）

## 阶段 3：领域微调（SFT/DPO/GRPO）

- **学什么**：SFT 和预训练的区别？DPO 和 GRPO 是什么？为什么微调不能提升"事实正确性"？
- **做什么**：构造领域数据 → SFT（LoRA）→ DPO → GRPO（规则 verifier）
- **产出**：`src/train/` 的训练脚本
- **坑**：① 50 步 SFT 收益有限、DPO 会过拟合（本项目实测）；② 合成数据难迁移到真实长文本

## 阶段 4：多模态（视觉语言模型）

- **学什么**：VLM 能"看图说话"，但做不了像素级检测
- **做什么**：Qwen3-VL 看影像、双时相变化检测、变化图 → 实验报告
- **产出**：`src/vlm/` + `eval_vlm.py`（变化检出 100%、定位 85%）
- **坑**：① 评测标准要公平（质心匹配 40% → 变化区域覆盖 85%）；② 输出会回显 prompt，解析要小心

## 阶段 5：Agent + 自主工具调用

- **学什么**：什么是 tool-calling？"路由分发"和"自主决策"的区别？
- **做什么**：把能力封装成工具，让 LLM 用 function-calling 自主决定调哪个
- **产出**：`src/agent/agent_toolcall.py`
- **坑**：模型加载很吃显存，要共享模型、惰性加载

## 阶段 6：MCP + 工具系统

- **学什么**：MCP（Model Context Protocol）是什么？为什么工具要协议化？
- **做什么**：用 FastMCP 把工具暴露成标准 MCP server，任何客户端都能调
- **产出**：`src/agent/mcp_server.py`

---

## 总结：一条完整能力链

```
RAG(检索) → 评测(证明) → 微调(对齐) → 多模态(看图) → 工具调用(自主) → MCP(标准化)
```

做完这 6 步，你就拥有了一个**可部署、可评测、可写进简历**的领域 Agent，以及一条完整的 LLM Agent 开发经验。

## 附录：核心概念详解

### A. BM25 是什么

**BM25 是经典搜索引擎的核心算法**，属于「关键词/词法检索」（sparse retrieval）。你输入几个词，它给每篇文档打分，看文档跟查询「字面上」多匹配。它是 TF-IDF 的升级版，几乎所有混合检索系统里都有它。

**打分看三件事：**

1. **词稀不稀有（IDF）**：查询里的词越罕见越有区分度，权重越高。
2. **出现多少次（TF，带饱和）**：出现多 → 相关，但非线性（出现 10 次只比 3 次略高，防堆词作弊）。
3. **文档长度归一化**：同样出现一次，短文档比长文档更相关。

**公式（看结构即可）：**

```
BM25(查询,文档) = Σ 对每个查询词 t：
    IDF(t) × [ TF(t,文档) × (k1+1) ] / [ TF(t,文档) + k1 × (1 - b + b × 文档长度/平均长度) ]
```

- `IDF(t)`：词 t 的稀有度；`TF(t,文档)`：词 t 出现次数；`k1≈1.5`、`b≈0.75`：可调参数。

**优缺点：**

| ✅ 擅长 | ❌ 不擅长 |
|---|---|
| 精确词匹配（"LEVIR-CD"就是"LEVIR-CD"） | 语义相似（"遥感" vs "satellite"不认识） |
| 专有名词、数据集名、方法名 | 同义词、改写、意译 |
| 快、可解释、零训练 | 长尾语义 |

**所以现代系统都是 BM25 + 向量检索混合**：BM25 抓精确词，向量抓语义，互补。

### B. 为什么语义检索对「数字题」天然失效（数字感知检索的根因）

这是本项目最重要的一个发现，讲透它比 97.2% 这个数字更值钱。

**现象**：问「这篇论文的 F1 是多少」，普通 RAG 数字忠实只有 17.4%，而换三种分块（1354/7683/27977 块）都救不了（17~20%）。

**根因**：检索靠「语义相似度」，但数字题要的是「精确值」：

- 向量检索找的是"语义上最像『F1 分数』的句子" → 论文里 "F1=0.90" / "F1=0.85" / "IoU=0.81" 语义上**一模一样**（都是"某指标=某数"），几乎等距。
- BM25 也一样：词 "F1" 命中所有含 F1 的句子，而区分答案的数字（0.90 vs 0.85）在问题里**根本没出现**。
- **关键矛盾**：问题给的信息太少（只说"F1 是多少"），不足以让检索器在几十个"F1=某数"里挑对的那个。

**解决（数字感知检索）**：既然语义/词法检索对数字天然失效，就**绕开它**——索引时用正则把「字段=数字」抽成结构化表，数字题查表拿精确值，不让向量去"猜"。这才从 17.4% 跳到 89.7%（换 Qwen3-8B 后 97.2%）。

**一句话**：不是分块粗、不是 BM25 弱，是"精确值"这类答案，语义检索和词法检索都天生给不了，必须结构化查表。
